# 测试编写约定

本文定义本仓库当前的测试代码约定。它是项目协作规范，不替代 Rust 2024 语言本身的测试规则。

## 1. 测试归属

| 类型 | 位置 | 适用范围 |
| --- | --- | --- |
| 单元测试 | 被测模块所在的 `src/**/*.rs`，使用 `#[cfg(test)]` | 验证一个模块或领域类型的行为；可以访问私有实现细节。 |
| 集成测试 | `tests/<subject>.rs` | 验证公开接口或多个组件组成的完整调用链。 |
| 测试 fixture | `tests/<subject>_fixtures/` | 只提供对应测试入口需要的假工具、固定选择器或固定参数生成器。 |

按被测对象而不是测试中恰好出现的类型归类：例如，注册与读取工具的行为属于 `ToolRegistry` 单元测试；工具本身的输入输出属于工具测试；选择、参数生成和工具调用串联起来的行为属于 `Runtime` 集成测试。

每个集成测试入口都是独立 crate。不要为了复用少量代码而让所有入口加载一个宽泛的 `common` 模块；应将 fixture 缩小到实际使用范围，避免无关的 `dead_code` 告警和隐式依赖。

## 2. 测试函数命名

测试函数使用行为导向的 `should_...` 命名：

- 有明确条件时使用 `should_<预期行为>_when_<条件>`。
- 条件已由名称自然表达时可以使用 `should_<预期行为>`。
- 名称描述可观察结果，不描述实现步骤。

例如：

```rust
fn should_return_stale_for_mismatched_job_without_writing() {}
fn should_preserve_tool_call_order() {}
```

## 3. 测试函数注释

每个测试函数都使用两段文档注释：第一段直接说明验证的行为；第二段以“方法：”简述如何构造场景和检查结果。

```rust
/// 验证重复提交同一 Job 不会覆盖先前保存的输出。
///
/// 方法：先成功提交，再重放相同 Job，并比较两次提交间的快照。
#[test]
fn should_not_commit_same_job_twice() {}
```

注释应描述业务语义和测试方法，而不是逐行复述实现。

## 4. 场景与断言

- 一个测试验证一个明确行为或领域不变量。一个原子操作影响多个字段时，可以在同一测试中断言这些字段。
- 不为同一个行为保留多个近似测试；优先合并为表驱动测试，例如边界值、状态枚举或同一错误分支的多个输入。
- 已由其他测试验证的通用结果不重复断言。若某个更窄的测试刻意省略该断言，可用简短注释说明覆盖位置。
- 重复的准备、读取、快照或错误断言应提取为局部辅助函数。辅助函数应表达领域意图，例如 `saved_task`、`assert_task_and_plan_unchanged`，而不是隐藏关键业务判断。
- 多个独立效果可以使用多个断言；不要为了减少断言数量而降低失败诊断质量。对完整对象、序列或错误记录可优先比较快照。

## 5. Fixture 与失败信息

- 测试数据、固定依赖和运行时专用测试工具应放在贴近被测入口的 fixture 模块中。
- fixture 的可见性保持最小；只有返回类型必须暴露给测试 crate 时才使用 `pub(crate)`。
- 对预期成功的准备步骤使用带上下文的 `expect("...")`，对预期失败的分支使用 `expect_err("...")`；不要使用无说明的 `unwrap()`。
- 不使用 `#[allow(dead_code)]` 掩盖无关 fixture。应缩小模块范围或删除未使用的支持代码。

## 6. 提交前验证

修改测试或生产代码后，在仓库根目录运行：

```bash
cargo fmt --all -- --check
cargo test --workspace
cargo clippy --workspace --all-targets -- -D warnings
git diff --check
```

只有这些检查全部通过，测试代码才视为符合本仓库约定。
