# LLM-Driven Runtime

一个 LLM 当作任务编排核心的运行时项目，使用 Rust 编写。

下面我按你一开始的规格说明风格，把最新设计重新整理一版。我会尽量只保留必要概念，并把一些名称换得更准确。

---

## Agent 执行模型

Agent 的一次执行由三个阶段组成：

1. **决策**：决定下一步使用哪个工具
2. **参数生成**：为选中的工具生成调用参数
3. **执行**：后端校验并执行工具，更新当前状态

工具执行成功后重新进入决策阶段，直到任务完成或需要等待用户输入。

系统维护一个 **当前状态 State**，用于记录当前任务已经获得的事实、执行结果，以及当前任务已经加载的业务知识。

业务知识本身长期存储在 **知识源** 中，后端根据当前任务按需加载到 State。

---

## 1. 决策

### 输入

后端向 LLM 输入下面的内容：

1. **用户需求**
2. **当前状态**

   * 当前任务已经获得的事实
   * 已执行工具及其结果
   * 当前任务已经加载的业务知识
   * 待用户确认的工具调用（如果存在）
3. **当前阶段描述**

   * 当前阶段的目标
   * 输出结果的 schema
4. **工具卡片**

   * 工具用途
   * 触发场景
   * 调用条件
   * 执行后对当前状态的影响
   * 是否需要用户确认
5. **上次错误**

   * 如果上一次决策失败，则提供失败原因

在向 LLM 提供工具之前，后端对工具进行筛选：

1. **权限筛选**

   * 过滤用户无权使用的工具
2. **相关性筛选**

   * 根据用户需求、当前状态和当前业务上下文，筛选可能相关的工具
   * 相关性筛选以避免遗漏正确工具为优先

如果当前 State 中缺少理解用户需求所需的业务知识，后端先从知识源获取相关知识并补充到 State，再进行工具筛选和决策。

---

### 输出

LLM 根据当前阶段描述中的 schema，输出下一步选择的工具。

例如：

```json
{
  "tool": "check_task_status"
}
```

LLM 返回结果后，后端进行下面的校验：

1. **JSON 校验**

   * 能否解析出符合要求的 JSON
2. **存在性校验**

   * 工具是否存在
3. **权限校验**

   * 用户是否有权限调用该工具
4. **可调用性校验**

   * 根据当前 State，该工具当前是否允许调用

如果校验失败，则把错误原因作为下一次决策的输入重新交给 LLM。

---

## 2. 参数生成

### 输入

确定工具之后，后端向 LLM 输入下面的内容：

1. **用户需求**
2. **当前状态**
3. **当前阶段描述**

   * 当前阶段的目标
   * 输出结果的 schema
4. **工具调用 schema**

   * 参数名称
   * 参数描述
   * 参数类型
   * 是否必需
   * 示例
   * 取值范围
5. **上次错误**

   * 如果上一次参数生成失败，则提供失败原因

---

### 输出

LLM 根据工具调用 schema 输出工具参数。

例如：

```json
{
  "task_id": "xxx",
  "limit": 10
}
```

后端对参数进行下面的校验：

1. **JSON 校验**

   * 能否解析出完整 JSON
2. **参数存在性校验**

   * 必需参数是否存在
   * 是否包含不存在的参数
3. **类型校验**

   * 参数类型是否正确
4. **范围校验**

   * 参数值是否符合 enum、范围、格式等限制
5. **业务前置条件校验**

   * 当前 State 是否满足该工具的调用条件

如果校验失败，则把错误原因作为下一次参数生成的输入重新交给 LLM。

---

## 3. 执行

参数校验成功后，后端准备执行工具。

### 用户确认

如果工具不需要用户确认：

```text
直接执行工具
```

如果工具需要用户确认：

```text
生成完整工具调用
↓
保存到当前 State
↓
向用户展示即将执行的操作及关键参数
↓
等待用户确认
```

State 中保存：

```json
{
  "pending_tool_call": {
    "tool": "xxx",
    "arguments": {
      "...": "..."
    }
  }
}
```

用户确认后，后端直接执行已经保存的 `pending_tool_call`。

**不得重新让 LLM 生成参数。**

因为用户确认的是一个具体的工具调用，而不是抽象的操作意图。

如果用户修改了条件，则原 `pending_tool_call` 失效：

```text
用户修改需求
↓
更新 State
↓
清除 pending_tool_call
↓
重新进入决策阶段
```

---

### 工具执行

执行工具后：

#### 执行成功

后端：

1. 获取工具执行结果
2. 根据工具定义更新 State
3. 清除已经完成的临时状态
4. 重新进入决策阶段

流程为：

```text
决策
 ↓
参数生成
 ↓
执行
 ↓
更新 State
 ↓
决策
 ↓
...
```

因此，一个需要多个工具完成的复杂任务，本质上只是这个循环执行多次。

---

#### 执行失败

如果工具执行失败，后端根据错误性质处理：

* 参数或业务条件仍有问题：重新进入参数生成或决策
* 当前工具不再适用：重新进入决策
* 临时性系统错误：由后端直接重试
* 缺少用户输入：向用户请求补充信息
* 无法继续完成任务：结束执行并向用户说明原因

只有需要语义判断的失败才重新交给 LLM。

确定性的错误处理由后端完成。

---

## 4. 当前状态

State 是 Agent 当前任务的唯一工作状态。

它可以包含三类信息：

### 当前事实

例如：

```json
{
  "task": {
    "exists": true,
    "status": "normal"
  }
}
```

表示 Agent 已经从工具执行中获得的事实。

---

### 当前任务所需的业务知识

例如用户提出：

> 帮我完成 xxx 任务的完整性检查

后端从知识源获取：

```json
{
  "knowledge": {
    "task_integrity_check": {
      "requirements": [
        "任务存在",
        "任务状态正常",
        "存在至少一个运行成功案例"
      ]
    }
  }
}
```

之后的多轮执行都可以继续使用这份知识，不需要根据每一句用户输入重新获取。

因此：

> **知识源保存长期业务知识，State 保存当前任务实际需要使用的业务知识。**

---

### 当前执行状态

例如：

```json
{
  "integrity_check": {
    "existence": "pass",
    "status": "pass",
    "successful_run": "unknown"
  }
}
```

这样可以区分：

```text
unknown = 尚未检查
pass    = 已检查并通过
fail    = 已检查但不通过
skipped = 根据业务规则无需检查
```

避免把“还没执行”和“执行结果为 false”混为一谈。

---

## 5. 业务知识

业务知识用于解释：

> **用户表达的业务概念到底意味着什么。**

例如：

```text
“任务完整性检查”
```

对应的业务知识可能是：

```text
完整性检查通过条件：

1. 任务存在
2. 任务状态正常
3. 至少存在一个成功运行案例
```

业务知识应该尽量描述：

> **什么条件成立时，业务目标算完成。**

而不是描述：

```text
第一步调用 A
第二步调用 B
第三步调用 C
```

也就是说：

```text
Knowledge 定义业务规则
Tool 定义系统能力
LLM 决定如何利用能力满足业务规则
```

如果未来增加一个工具，可以一次获得所有完整性检查信息，业务知识无需改变。

---

## 6. 工具

每个工具包含两部分描述。

### 工具卡片

供决策阶段使用，描述：

```text
名称
用途
触发场景
调用条件
执行结果
是否需要确认
```

例如：

```text
check_task_runs

用途：
查询任务运行历史。

调用条件：
任务必须存在。

执行结果：
获得任务历史运行案例。
```

---

### 工具调用 Schema

供参数生成阶段使用，描述：

```text
参数名称
参数含义
类型
是否必需
范围
示例
```

工具本身只描述：

> **系统能够做什么。**

不要把具体业务流程写入某个工具。

---

## 7. 整体运行流程

最终整个 Agent 可以压缩成：

```text
                ┌───────────────┐
                │   用户输入     │
                └───────┬───────┘
                        ↓
                ┌───────────────┐
                │    Runtime    │
                │               │
                │ 补充业务知识   │
                │ 筛选候选工具   │
                └───────┬───────┘
                        ↓
                ┌───────────────┐
                │     决策       │
                │  选择下一工具   │
                └───────┬───────┘
                        ↓
                ┌───────────────┐
                │    参数生成    │
                └───────┬───────┘
                        ↓
                    后端校验
                        ↓
                 是否需要确认？
                  /           \
                是             否
                ↓              │
           保存待执行调用        │
                ↓              │
             用户确认            │
                └──────┬───────┘
                       ↓
                ┌───────────────┐
                │    执行工具    │
                └───────┬───────┘
                        ↓
                   更新 State
                        ↓
                       决策
```

## 核心职责

整个设计最终可以归纳成四个运行概念和一个外部数据来源：

| 组件                   | 职责                          |
| -------------------- | --------------------------- |
| **State**            | 保存当前任务已经知道什么、做到哪里以及当前所需业务知识 |
| **Tool**             | 定义系统能够做什么                   |
| **LLM**              | 根据用户目标、State 和工具决定下一步，并生成参数 |
| **Runtime**          | 控制上下文、校验、确认、执行和 State 更新    |
| **Knowledge Source** | 长期保存业务概念和业务规则，按需提供给 Runtime |

最核心的运行逻辑仍然很简单：

```text
选择
→ 填参
→ 校验
→ 确认（必要时）
→ 执行
→ 更新状态
→ 再选择
```

而复杂业务并不会引入新的执行模型：

> **复杂任务 = 这个循环执行多次。**
> **业务知识 = 告诉 Agent 什么才算完成。**
> **State = 告诉 Agent 当前已经完成了什么。**
> **Tool = 告诉 Agent 可以通过什么手段继续推进。**
